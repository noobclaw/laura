# 大型遊戲製作

適用範圍：有多個互相依賴的系統、大量關卡或內容、多人連線、開發期超過一兩個月的遊戲。

不適用：單局幾分鐘、一兩個人幾週能做完的手機休閒遊戲，改用 `casual-game-production`。

開工前先確認一件事：人力、資金和時間撐不撐得起。撐不起就把範圍砍到撐得起，或改做小遊戲。這個判斷在第一階段做，不要做到一半才發現。

---

## 一、五條不能破的規矩

1. **說話要有根據。** 數據、授權、平台規則、參考遊戲的規則都要附來源並分級（見第三節）。自己的判斷標明是判斷。沒驗證的說沒驗證。
2. **先寫清楚再動手。** 沒有通過的簡報或設計文件，不寫正式程式。原型程式可以隨便寫，但原型程式不進正式專案。
3. **範圍只能換，不能加。** 加一個功能就要砍一個同等大小的，或明確延期。每次範圍變動記錄是誰決定的。
4. **做之前先能看到自己的輸出。** 製作者（人或 AI）必須能在幾秒內開啟遊戲、截圖、看圖。看不到輸出的技術路線不選。每個玩家看得到的改動，都要實際開起來、截圖、看過才算完成。
5. **精美度有最低標準。** 畫面要達到參考作《星隕戰紀 Starfall》（sanwan.ai/games/xingyun-moba，公開復刻版 vileosbot-bot/starfall-rebuild）的水準：真 3D 場景配光照和陰影、完整的環境、有細節的模型、成品水準的介面、靜止時畫面也是活的、操作有即時反饋。那個遊戲的美術和音效全部是程式生成的，「沒有美術素材」不是做不到的理由。原型的灰模只能內部用。交付前把自己的截圖和參考作並排比，明顯差一截就不交。

## 二、階段和關卡

共八個階段。每階段結束有一道關卡，結論只有四種：

| 結論 | 意思 | 能不能往下 |
|---|---|---|
| 通過 | 所有必要項目都有證據 | 能 |
| 有條件通過 | 列出條件和期限 | 能，條件到期要回查 |
| 不通過 | 有必要項目失敗 | 不能 |
| 未評估 | 沒有人實際驗證過（例如沒人玩過） | **不能**，未評估永遠不算通過 |

關卡依規定由人確認。擁有者明說「不要停下來問」時，照指示往下做，但記錄寫「依擁有者指示推進」，不能寫「評審通過」。

### 階段 0：一頁簡報

目的：在任何程式之前，把「到底要做什麼」說清楚。

做法：問擁有者一輪問題（一次問完，每題附一個常見答案，讓對方可以回「你決定」），然後寫一頁簡報。

簡報九節：
1. **你的原話**：擁有者怎麼說的，一字不改保留。
2. **外觀與參考**：參考哪幾個遊戲或畫面，各取什麼、避開什麼。
3. **前一分鐘**：玩家打開遊戲第一分鐘看到什麼、做什麼。
4. **挑戰**：難在哪裡、怎麼輸。
5. **核心循環**：30 秒、一局、一晚三個層級在做什麼。
6. **功能**：這一版要有的。
7. **保留**：擁有者說一定要的（之後每次改動都要對照）。
8. **避開**：擁有者說不要的（同上）。
9. **最接近的現有遊戲**：寫出遊戲名，以及我們和它不同在哪。寫不出不同就是抄。

關卡：擁有者讀過簡報說「做」，或改了再說「做」。

### 階段 1：概念與拋棄式原型

目的：回答「這好不好玩」和「做不做得出來」。

交付物：
- 概念文件：一句話定位、目標玩家、核心循環、三到五個設計支柱、反支柱（明確不做的）、和同類作品的差異。
- 市場依據：同類作品的銷量或排名，附來源。
- 資源估算：要多少人、多久、多少錢，手上實際有多少。
- **拋棄式原型**：針對最危險的假設各做一個，一個原型只回答一個問題，最多一天。原型做完給擁有者玩。

原型的結論只有四種：**繼續、轉向、放棄、未評估**（沒人玩過）。
- **同一個概念轉向三次，強制做放棄或繼續的決定。** 問自己：這是對的點子，還是我捨不得已經花的時間？
- 做兩三個不同方向的原型挑最好的，勝過把一個方向改到死。
- **大的方向改變（換主角造型、換主題、換引擎）之前，先做幾張並排的概念圖或草模給擁有者選**，選定了才動正式程式。草模半小時能做，重做正式版要好幾天。
- 多人連線遊戲：本機原型只能證明機制有不有趣，不能證明連線下手感好。那要真人連線或模擬延遲。

關卡：擁有者玩過原型，結論是「繼續」。

### 階段 2：前期製作（設計與技術）

目的：把剩下的未知數變成已知。

交付物：
- **系統清單**：每個系統的層級（基礎／核心／功能／表現／打磨）、優先級（必須／應該／可以）、依賴、設計順序。
- **每個系統一份設計文件**，八節：
  1. 概要
  2. 玩家想要的感受
  3. 規則（逐條，每條標出處級別）
  4. 公式與數值範圍
  5. 邊界情況
  6. 和其他系統的依賴
  7. 可調參數（放在數據檔，不寫死在程式）
  8. 驗收條件（可以用腳本或截圖證明的句子）
- **美術規格**九節：視覺定位一句話、氛圍、形狀語言、色彩系統、角色、場景、介面、素材標準（三角面數、貼圖大小、繪製呼叫預算）、參考方向（取什麼、避開什麼）。
- **技術架構文件**：分層（純規則／模擬／連線／渲染／介面／音效／數據／工具）。規則層要能脫離引擎單獨跑測試。
- **技術決策記錄**：每個重大選擇一份，寫背景、選項、決定、後果、怎麼驗證。
- **引擎和版本鎖定**，第三方函式庫固定版本、放進專案，不從網路即時載入。
- **風險清單**：每條寫可能性、影響、對策、負責人。
- **證據表**（做復刻或參考其他遊戲時必備，見第三節）。

技術選型的第一個問題：**製作者能不能自己看到輸出？** 能在本機用無頭瀏覽器或引擎命令列截圖的路線優先。一天只能看一次雲端打包結果的路線，品質一定上不去。

關卡：每個「必須」級系統都有設計文件；架構和決策記錄寫好；核心規則的自動測試和持續整合（CI）建好。

### 階段 3：垂直切片

目的：做出一小段達到最終品質的完整體驗。

交付物：10 到 30 分鐘的可玩內容，包含所有核心系統，美術、音效、介面都是成品水準。拆成依序建造的任務清單，每條有完成的定義。

要求：
- 用正式架構做，不是原型的延續。
- 找沒看過的人試玩，不給口頭說明，記錄卡在哪。
- 測量做這段實際花了多少時間，用它推算全部內容要多久。
- 切片報告的五節：要回答的問題、做了什麼、每個任務的證據、沒驗證的、結論。**結論欄在有人玩過之前一律寫「未評估」。**

關卡問題：陌生人能不靠指導玩完嗎？他們想繼續玩嗎？按這個速度做得完嗎？做不完就在這裡砍範圍。

### 階段 4：製作

目的：按切片標準量產全部內容。

做法：
- 史詩和任務。每個任務有驗收條件、依賴和估時。
- 衝刺制，每個衝刺兩週左右（單人可縮成一週）。衝刺開始定範圍，結束做回顧。
- 一次一個功能：說清楚要做什麼 → 做 → 開起來看 → 測試 → 提交。
- 每個任務完成的定義：功能實作、測試通過、**截圖看過並存檔**、符合設計文件、沒引入已知的嚴重缺陷。
- 設計變更先改設計文件，再通知所有依賴它的系統，最後改程式。不准先改程式、文件之後補。
- 每個里程碑評審一次：進度對照計畫、品質對照切片、範圍要不要調。

程式規則：
- 玩法數值放數據檔。要調手感時做一個調整面板，每個數值一根滑桿。
- 介面由事件驅動，不每幀輪詢遊戲狀態。
- 不手改引擎生成的場景檔和資源元數據。
- 規則層有單元測試，合併前跑冒煙測試。
- 隨機一律用固定種子，同一個種子永遠得到同一局，方便回歸比對。
- 每次改動後用同一個種子重跑同一段，畫面或結果有變就給擁有者看。

內容規則：
- 關卡先教後考：一個空間教一個機制，下一個考它，再下一個和舊機制組合。
- 數值平衡用表格和模擬驗證，不靠感覺。
- 素材按美術規格驗收。每個素材登記來源和授權。

### 階段 5：打磨

目的：不加新功能，只提高品質。

順序：
1. **性能**：在目標硬體上測幀率、記憶體、載入時間，對照預算列優化清單。軟體渲染測到的數字不算數，要真顯示卡。
2. **優化**：每項記錄前後數據。
3. **視覺**：特效一致性、鏡頭、反饋手感。效果在低配置能降級。
4. **音效**：有沒有動作缺聲音、混音過大或過小、環境音層。**沒有人耳聽過的音效和音樂，不能說好聽。** 程式合成的音樂風險很高，聽感不行時改用有授權的曲子或外包。
5. **加固**：邊界輸入、快速連點、長時間運行、連續玩多局、壓力測試、回歸測試。

反饋手感：按事件分小、中、大三級，同級同強度。震動只動鏡頭。命中停頓用真實時間計時。大面積閃光每秒不超過 3 次。提供震動強度和減少閃光設定。

關卡：每項指標達到預算。沒有測量的指標標「未評估」，不算通過。

### 階段 6：上線

上線檢查表全部打勾：
- 各平台認證要求逐條核對（Steam、各主機、各商店）。
- 年齡分級、隱私政策、數據收集聲明。
- 第三方程式碼和素材的授權清單與署名。
- 多語言：字型覆蓋、文字溢出、術語一致、由右至左語言。
- 無障礙：字幕、色盲模式、按鍵重綁、字體大小。
- **文化與地區敏感度**：目標市場不接受的字眼、符號和圖案逐張貼圖檢查（例如對華語市場：旭日類圖案、標榜國別的文案）。
- 存檔相容與損壞恢復。
- 崩潰回報與數據統計接通並驗證。
- 首日修補計畫和回滾方案。
- 商店頁、截圖、預告片、關鍵字。
- 桌面版程式簽章（macOS 要 Developer ID 憑證並公證，否則玩家會看到安全警告）。

### 階段 7：營運

- 上線第一週每天看崩潰率、留存、評價。
- 缺陷分四級，最高級走緊急修補。
- 每次更新寫更新說明並做回歸測試。
- 定期回顧：哪些估算錯了、為什麼、下次怎麼改。

## 三、參考其他遊戲時：證據表

做復刻或「玩法照某遊戲」的專案，**在寫任何規則之前**先建證據表，之後所有規則都從這張表來。

每條寫：項目、內容、級別、出處網址。

| 級別 | 來源 | 怎麼用 |
|---|---|---|
| A | 開發者本人說的，或多家媒體轉述同一則官方公告 | 照做 |
| B | 兩個以上攻略站一致，或擁有者親自玩到、截圖、錄影 | 照做 |
| C | 只有一個來源，或來源互相矛盾 | 照做並在文件標記 |
| ？ | 查不到 | 我們自己定，文件寫明是自己定的 |

規則：
- **拿不準就照原作做。** 自己發明的規則全部做成選項，預設關閉，集中放在「自訂規則」。
- 擁有者親自玩到的說法優先於攻略站。擁有者貼來的資料要查證，查證結果寫進證據表。
- 每份設計文件的每條規則標上級別。
- 做一張對照清單：原作的每條規則 → 已做／部分／缺／故意不同（附理由）。缺的和部分的先補，再做自己的創新。
- 只看公開資料：媒體、攻略、開發者貼文、玩家討論、影片。不下載、不反編譯原作，不碰外掛和修改器的程式碼。
- 原作的角色、地圖、介面圖樣、名稱、文案都不照搬；照搬的是功能和規則。商店頁不提原作名稱。

## 四、驗證方法

### 看得到才算數
每個玩家看得到的改動：
1. 用固定解析度（預設 1280×720）直接開到那個場景。功能要能用網址參數或啟動參數直接開到，不能只能從主選單點三層進去。
2. 等畫面穩定，截圖，存進證據資料夾。
3. **打開截圖看**：文字有沒有被切、面板有沒有溢出、元素有沒有少、顏色對不對。
4. 截圖沒看過就不算證據。

### 驗收清單
簡報和設計文件的每一條都是一個項目，標成：通過／缺／壞／未評估，附證據（截圖檔名或程式位置）。未評估一定寫原因。

### 用數字量，不靠感覺
「好不好藏」「順不順」「會不會卡」這類問題，先寫一個量測腳本再改：
- 偽裝效果：同一位置貼著表面的角色和表面的色差。
- 流暢度：鏡頭每幀不是由輸入造成的位移、速度變化量。
- 卡住：讓角色沿每面牆、穿過每扇門走一遍，記錄停住超過一秒的次數。
- 改之前量一次、改之後量一次，兩個數字都報告。

### 一定要有的整體測試
- **連續玩三局**：每局結束能回大廳、能開下一局。
- **碰撞圍堵**：角色沿每面牆爬、繞每個轉角、推每種物件，確認不會穿出可玩範圍、不會嵌進物件。加一道保險：跑出範圍就拉回最近的合法位置。
- **乾淨複製**：從 Git 重新複製一份，確認能跑（防止被忽略規則漏掉檔案）。
- **錯誤不讓遊戲卡死**：每幀出錯要記錄並繼續，畫面角落顯示錯誤，方便玩家截圖回報。

### 冒煙檢查（約五分鐘）
開得起來、沒有錯誤、截圖看過、按幾個鍵畫面有反應、文字不重疊不出界、畫面不會凍結、結束畫面能離開。修一輪，再跑一次；還壞的寫進報告「仍然壞掉：……」。

## 五、團隊與審查

人少時一個人兼多個角色，但每個角色的責任都要有人擔。

| 角色 | 負責 | 審查時看什麼 |
|---|---|---|
| 創意總監 | 設計支柱、整體體驗 | 支柱有沒有被違反、玩家感受對不對 |
| 技術總監 | 架構、技術選型、性能預算 | 系統邊界、決策記錄、引擎風險、改動影響 |
| 製作人 | 排期、範圍、風險 | 範圍和時程、里程碑風險 |
| 美術總監 | 美術規格、素材驗收 | 視覺一致性、精美度標準 |
| 音效總監 | 音樂音效方向、混音 | 聽覺是否達標（要人耳） |
| 系統、關卡、敘事設計 | 各自的設計文件和內容 | 各自領域 |
| 玩法、引擎、介面、工具程式 | 各自的程式 | 實作方式 |
| 測試負責人 | 測試計畫、缺陷分級 | 能不能發布 |

審查強度三檔：**完整**（每個關卡各角色都審）、**精簡**（只審階段關卡）、**單人**（自審，記錄為自審）。

規則：
- 跨領域衝突交給共同上級決定，不私下妥協。
- 評審的人不能是寫的人。高風險的成品由沒參與製作的另一個人或代理檢查。
- 測試的任務是找出怎麼壞，不是確認沒壞。

### 用 AI 代理製作時
- **一個模組只有一個負責的代理。** 同時開多條線時，每條線用獨立的工作目錄和分支，寫明它可以改哪些檔案、不准碰哪些。
- **小步提交、立刻推送**，至少每 30 分鐘一次。服務可能中途重啟，沒推送的進度會丟。
- 每次改動只跑相關的檢查；完整測試一小時最多跑一次，收尾時跑一次。
- 代理的工作記憶快用完時，停在乾淨的提交上，寫交接：做了什麼、證據、沒做什麼、下一步。
- 交接報告要有：可以發布的提交、每項的證據、哪些用眼睛看過／用腳本驗過／完全沒驗、和規格不同的地方、沒做完的。
- 代理說「完成」不算數，要親自看截圖、跑一次乾淨複製的開機檢查，才發布給擁有者。
- AI 生成的程式和素材只算草稿，要經過和人寫的一樣的評審和測試。
- AI 生成的圖要檢查尺寸、透明度、裁切和風格一致性，並登記生成工具和修改過程。
- 上架平台要求披露 AI 生成內容時，如實披露。
- 讓 AI 操作引擎編輯器的插件，只裝有原始碼、能審查的；不含原始碼的不裝在有重要資料的機器上。
- 沒有在編輯器和目標平台實際跑過的結果，只能說是靜態審查，不能說通過。

---

## 六、範圍控制

- 每個功能標三檔：必須有、應該有、可以有。排期只保證第一檔。
- 每個里程碑對照實際速度和剩餘工作量，差距超過兩成就砍範圍或調日期，並記錄決定。
- 擁有者一次丟很多問題時：先全部記成編號清單、逐條寫下推測的原因，不動手；擁有者說「開始」再按順序做。
- 擁有者指定「做完這幾項就打包」時，只做那幾項，其他的排到打包之後。
- 砍功能時連它的設計文件、素材、程式一起標記移除，不留半成品。
- 技術債登記：在哪、為什麼欠、什麼時候還。

---

## 七、和擁有者溝通

- 被問「做完沒」：直接回答完成多少、還差什麼、各要多久（標明是估計），不要只說「在做」。
- 每完成一塊能玩的就更新試玩版並說改了什麼；做到一半的版本不發。
- 每次交付都說清楚：
  - 做了什麼，對應哪份文件的哪一條。
  - 驗證過什麼、怎麼驗的、結果。
  - 沒驗證什麼、為什麼。好不好玩、手感、聲音、真實硬體效能，在擁有者玩過之前一律寫「未經人玩過」。
  - 已知問題和嚴重度。
- 自己做錯就直接說錯在哪、怎麼改，不找理由。
- 擁有者的回饋是最高優先的證據，比任何攻略和自己的判斷都重要。
