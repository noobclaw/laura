## 🔴 阻断项

### R1. 远地手动机位:一半事件显示「—」(日出/晨黄金/晨蓝调全空)
- **文件:行**:`lib/tool/astro.dart:313-355`(`computeDayLight` 用 `DateTime(localDate.y,m,d)` 即**设备本地**零点为窗口起点采样 1440 分钟;`cross()` 只在全局最高点 `maxIdx` 之前找上升穿越、之后找下降穿越)。
- **现象**(脚本实测,设备 UTC+8):
  - 纽约 40.71N 74.01W 2026-06-21:`dawnCivil / goldenStartAm / sunrise / goldenEndAm` 全为 null,`solarNoon` 显示 00:58,`moonrise` null。UI 上时间轴前四行「—」、hero 日出「--:--」。
  - 伦敦 51.5N 0.12W:反过来,`goldenStartPm / sunset / goldenEndPm / duskCivil` 全 null——日落「—」。
  - 东京(时差 1h)正常。即:**机位与设备时差 ≳ 6h 就必坏**。
- **根因**:设备本地 00:00–24:00 这个窗口对应纽约当地 12:00–次日 12:00,只含一个「下午+夜晚+上午」,上升穿越落在 `maxIdx` 之后(被 `rising` 循环范围排除),下降穿越又在 `maxIdx` 之前。这不是显示时区问题,是**采样窗口选错了一天**,「按设备时区显示」的注记(`light_view.dart:307-312`)掩盖不了。
- **真机复现**:机位页 → 添加机位 `40.71, -74.01` → 今日页看时间轴:日出行为「—」。
- **修法**(推荐 A):把「一天」定义为**机位的太阳日**而非设备日历日——`estOffsetH = (lon / 15).round()`(或用 `lon/15` 不取整),`dayStartUtc = DateTime.utc(y,m,d).subtract(Duration(hours: estOffsetH))`,采样 24h 后事件时刻加回 `estOffsetH` 显示,并在 `_LocationHeader` 把「按设备时区显示」改成「按机位估算时区 UTC+X 显示」(`light_view.dart:307-312`)。这同时解决 R2。备选 B:采样 48h(前一天 12:00 → 次日 12:00 设备时),以离目标日中午最近的那次 solar noon 为中心,在 [noon-12h, noon+12h] 内找穿越,并给跨日事件加「+1」/「-1」标记。

### R2. 高纬夏季:日落在次日 00:xx 的地方,日落/暮黄金/暮蓝调显示「—」(设备与机位同时区也会坏)
- **文件:行**:同 `astro.dart:314-327, 348-353`。
- **现象**(脚本用「经度平移到本机时区」的等价方式实测,即**模拟当地用户手机就在当地**):
  - 冰岛雷克雅未克 64.13N(真实:日出 02:55、日落 **次日 00:04**)→ 算法给日出 02:55 ✓、`goldenStartPm` 22:06 ✓,但 **sunset / goldenEndPm / duskCivil 全 null**。`polarDay=false`,所以 UI 不会出极昼横幅,只是三行「—」,hero 落到「清晨黄金时段」——用户傍晚打开 app 想查日落,看到「—」。
  - 费尔班克斯 64.84N(日落次日 00:47)同样 sunset null。
- **根因**:窗口以设备日历日截断,00:00 之后的事件永远找不到;`polarDay = minAlt > -0.833` 又不成立(该地夏至夜里太阳降到 -2.4°),于是既不算极昼、也没有日落。
- **真机复现**:任何 ≥ 62°N 的机位,选 6 月中旬日期(Pro)或直接在冰岛/阿拉斯加真机今日页。
- **修法**:与 R1 同一修法(以 solar noon 为中心的 ±12h 窗口),事件跨日时在时间轴显示「00:04 +1」。这是摄影 app 的核心客群(极光/午夜太阳),不能只靠极昼横幅兜底。

## 🟠 重要项

### O1. iOS 罗盘:定位未授权前 heading 恒为 -1 却被当作有效朝向
- **文件:行**:`lib/tool/sensors.dart:29-33`(只判 `e.heading == null`)。插件 `flutter_compass-0.8.1/ios/Classes/SwiftFlutterCompassPlugin.swift:45,86` 发的是 `CLHeading.trueHeading`,Apple 文档:trueHeading 需要该 CLLocationManager 同时有 location updates 才有效,否则为 **-1**;插件只过滤 `headingAccuracy > 0`,不过滤 -1。
- **现象**:iOS 首启(罗盘在 `goldenscout_tool.dart:69` 于定位授权前就启动)→ 收到 heading -1 → 盘面转 1°、图例写「罗盘已对齐你的朝向」(`light_view.dart:335-339`)——假对齐。授权并成功定位后一般恢复正常。
- **修法**:`if (e.heading == null || e.heading! < 0) { _heading = null; notifyListeners(); return; }`(Android 的 heading 范围是 (-180,180],故此过滤**只能在 iOS 上做**:`Platform.isIOS && e.heading! < 0`)。

### O2. Android 罗盘是磁北、太阳方位是真北,未做磁偏角校正;iOS 是真北——两端语义不一致
- **文件:行**:`sensors.dart:26-33`;插件 Android `FlutterCompassPlugin.java:178-215`(`TYPE_ROTATION_VECTOR` → `getOrientation` 方位角 = 相对**磁北**)。
- **现象**:Android 用户举手机对准盘面上的日落射线时,真实太阳偏 |磁偏角|:北京 ≈ 7°W、东京 ≈ 8°、旧金山 ≈ 13°E、冰岛 ≈ 14°、新西兰 ≈ 20°。商店文案「hold your phone up and the rose aligns to where you're pointing」在 Android 上是过度承诺。
- **修法**:Android 侧算磁偏角:最省事是加一个 10 行的 MethodChannel 调 `android.hardware.GeomagneticField(lat, lon, alt, millis).getDeclination()`(系统内置 WMM,离线),`heading + declination` 后再用;或纯 Dart 的 WMM 包(需核对离线与体积)。iOS 保持 trueHeading。图例加「真北」字样。

### O3. 无磁力计的 Android 设备会收到恒 0° 的 heading,app 宣称「已对齐」
- **文件:行**:`sensors.dart:29-33`;插件 `FlutterCompassPlugin.java:116-124, 177-182, 306-315`——无 rotation vector 时退回加速度计+磁力计,磁力计不存在时 `getRotationMatrix` 返回 false 但矩阵保持全 0 → `getOrientation` 给方位角 0,`accuracy` 恒 **-1**,事件照发。
- **现象**:廉价平板/无磁力计手机上盘面固定「正北朝上」但图例写「罗盘已对齐你的朝向」,PLAN 验收第 4 条「应有降级提示」不成立。
- **修法**:`if (e.accuracy != null && e.accuracy! < 0) → 视为无罗盘`(有 rotation vector 的机器注册时系统会先回调一次 onAccuracyChanged,accuracy 为 15/30/45);另外当 `accuracy >= 45`(LOW/UNRELIABLE)时图例提示「画 8 字校准罗盘」。

### O4. 罗盘无平滑、无死区:每个传感器事件都 `notifyListeners` → 盘面抖动
- **文件:行**:`sensors.dart:30-32`(每事件通知);Android 事件节流 32 ms(`FlutterCompassPlugin.java:35`),iOS `headingFilter = 0.1°`(`Swift:17`),即 30–60 Hz。
- **现象**:磁场稍有干扰(室内/靠近相机机身)盘面来回抖 ±2–5°,读方位数字时看不清。
- **修法**:在 `SensorHub` 做圆周指数平滑(对 sin/cos 各做 EMA 后 atan2 回来,α≈0.15),且 `|Δ| < 0.5°` 不通知。

### O5. `computeMoonTimes` 放在罗盘 `ListenableBuilder` 的 builder 里,每个罗盘事件重算一次
- **文件:行**:`lib/tool/light_view.dart:70-98`(`computeMoonTimes(...)` 在第 95 行 builder 内);`computeDayLight` 在 build 顶部第 63 行,每次 `setState`(30 s 定时器)也全量重算;`IndexedStack` 里 Today 与 Planner 两个 `LightView` 同时订阅传感器,离屏那份也在算。
- **实测成本**(本机 AOT):`computeDayLight` 146 ms、`computeMoonTimes` 29 ms;其中天文数学本身只占 1441×1.3 µs ≈ 2 ms,**大头是每个采样点 `dayStart.add()` + `t.toUtc()` 的本地时区换算**(`astro.dart:322-323, 416-417`)。Android 上 tz 换算比 Windows 快,但 30 Hz × 2 个视图 × 每次几百次 DateTime 换算仍是可感知的掉帧风险(未真机测,标为需验证)。
- **修法**:① 采样用 UTC 毫秒数算(`dayStartUtcMs + i*60000`,只在产出事件时转本地),消除每点换算;② `computeDayLight/computeMoonTimes` 结果按 `(date, lat, lon)` memo 到 State 字段,只在 `didUpdateWidget`/store 变化时重算;③ 把 `computeMoonTimes` 挪出 builder。

### O6. 购买结果只在「设置」页可见;从 Pro 弹层买/恢复时错误静默
- **文件:行**:`lib/core/purchase.dart:158-187`(`PurchaseNotices` 是 snackbar 的唯一出口),它只挂在 `goldenscout_tool.dart:29` 的设置项里;`pro.dart:47-51, 68-71` 从规划页/机位页弹出的 Pro sheet 直接 `buyPro()/restore()`。

### O7. 规划页 Pro 提示条硬编码「$3.99」,违反定价标准

### O8. 今日页跨零点后一直显示昨天(app 常驻时)

### O9. 定位失败提示没有「去设置」按钮

## 🟡 建议项

1. **月亮当前高度是地心值,未做视差修正**(`astro.dart:197-200, 79-90`):最多偏高 ~1°(地平线附近 0.95°)。月升/月落用的 +0.125° 阈值(`astro.dart:409`)是 Meeus 地心标准,**正确**;只是「当前月亮 高度 X°」显示会比肉眼高约 1°。修:`altTopo = alt - 0.95 * cos(alt)`(用 Schlyter 的 `mpar = asin(1/r)` 更准)。
2. **月相照亮百分比忽略黄纬**(`astro.dart:220-221`):误差 <0.2%,可不改;若改用 `cos(elong) = cos(β)cos(Δλ)` 顺手即可。
3. **hero 在傍晚黄金时段过后仍显示当天已过的窗口**(`light_view.dart:139-157`):22:00 打开 app 看到「傍晚黄金时段 19:05–20:06」。建议此时滚到明早的窗口并标「明早」。
4. **正午高纬冬季 noonAlt < 6° 时时间轴出现两行「—」无解释**(实测雷克雅未克 12-21 noon 2.4°:`goldenEndAm/goldenStartPm` null)。真相是「全天都是黄金光」,应显示「整日」而非「—」。
5. **DST 日窗口**(`astro.dart:314, 322`):`dayStart.add(Duration(minutes: i))` 是绝对时长,春季 23h 日多采样次日 0–1 点、秋季 25h 日少采 23–24 点。分析后认为在任何有人居住的纬度都不会漏事件,但修 R1/R2 时用 UTC 窗口顺便消除。
6. **手动坐标不接受逗号小数**(`location_screen.dart:228-229`):德/法/俄等区键盘 `numberWithOptions(decimal:true)` 出的是「,」,`double.tryParse('40,71')` 为 null → 永远报「请输入有效纬度」。修:`text.replaceAll(',', '.')`。
7. **免费用户空状态 CTA 只是切 tab**(`light_view.dart:688-692` → `goldenscout_tool.dart:86`):首启到看到光线要 3 次点击(选择机位 → 使用当前位置 → 授权)。建议空状态按钮直接触发 `currentFix()`。
8. **iOS 显示名与权限文案未本地化**:`ios/Runner/Info.plist:9-10, 71-72` 只有英文;Android 有 `values-zh/strings.xml`。加 `ios/Runner/zh-Hans.lproj/InfoPlist.strings`(`CFBundleDisplayName = "天光规划器"; NSLocationWhenInUseUsageDescription = "…"`)。
9. **Pro 弹层文案与实际门不符**(`pro.dart:34-36`「完整月亮详情:月升、月落与月相」):月相与照亮百分比免费可见(`light_view.dart:584-592`),锁的只有月升/月落(593-601)。改成「月升与月落时刻」,避免买后觉得没多东西。
10. **Pro 门可绕过的已知面**:① 改系统日期 → 今日页即任意日期(免费);② `goldenscout.json` 里 `pro:true` 明文(`location_store.dart:49, 75`),root/adb backup 可改。对 $3.99 买断可接受,记录即可;不建议加壳。
11. **启动竞态**:`PurchaseService.init` 的 restore 事件若早于 `store.load()` 完成(`main.dart:17` vs `location_store.dart:44-68`),`load()` 会用文件旧值把内存 `pro` 盖回 false(文件本身已是 true,重启恢复)。iOS StoreKit 启动时会派发未完成交易,概率低。修:`load()` 里 `pro = pro || (raw['pro'] ?? false)`。

## 五维度逐项结论

### 1. 产品设计
- **聚焦拍前查光**:兑现。三 tab(今日/规划/机位)+ 设置,今日页一屏:hero 黄金时段 → 罗盘 → 当前日月 → 9 行时间轴 → 月亮卡,没有多余功能。
- **免费层真可用**:是。今日 + GPS + **还能免费存 1 个手动机位**(`location_store.dart:17`,PLAN 只写「当前定位」,代码更慷慨,也让无 GPS 权限的用户仍能用)。
- **Pro 门位置**:合理。任意日期(规划页 `_shift/_pickDate` 双门)、第 2 个机位、月升/月落。**月亮不显残缺**:月相名+照亮%+盈亏免费可见,只锁两个时刻;但 Pro 弹层把「月相」也列为 Pro 权益(🟡9)——买后会觉得「就多了一行」。建议 Pro 权益改写为「月升/月落 + 任意日期 + 无限机位」,或把「月亮方位/高度轨迹」做成真正的 Pro 增量。
- **商店文案精度承诺**:「to the minute / 精确到分」经验证成立(≤1 min);「no network permission」已由 manifest `tools:node="remove"` 保证;**过度承诺的一句是罗盘**「hold your phone up and the rose aligns to where you're pointing」——Android 未校正磁偏角、iOS 未授权前恒 -1、无磁力计设备假对齐(O1–O3),建议改成「在支持罗盘的设备上」并修 O2。
- **楔子**:已知未过检索自检,不重复。仅补一点:代码确实比 PhotoPills 轻(今日页 ~2.5 屏滚动,无地图/AR/曝光),差异化在产品上是真的,缺的是商店证据。

### 2. 代码实现(装到真机上什么会坏)
- **定位权限流**:`sensors.dart:43-77`:服务关闭 → 提示;denied → 请求;deniedForever → 提示(含手动输入建议);denied → 提示。三种失败都有可见反馈 ✓,但缺「去设置」动作(O9),非 String 异常原样弹出(O9)。
- **GPS hang(b75baee)是否修透**:**修透了**。`getCurrentPosition(timeLimit: 20s)` 在 `geolocator_platform_interface` 是 Dart 侧 `.timeout()`,`geolocator_android-5.0.3:112-135` 超时还会 `cancelGetCurrentPosition` 取消原生请求 → `TimeoutException` → `getLastKnownPosition()` 兜底 → 再不行抛可读消息;`_locating` 在 `finally` 复位(`location_screen.dart:37-39`)。冷启动无信号:最多 20 s 转圈后必落地,不会永转。可改进:20 s 内没有任何进度文字/取消按钮(🟡)。
- **罗盘**:无磁力计降级错误(O3)、iOS -1(O1)、磁北/真北(O2)、抖动(O4)、后台不停(O11)。Android heading 范围 (-180,180] 传入 `compass_rose.dart:83` 的旋转公式数学上无问题。
- **持久化**:单 JSON,`_save` fire-and-forget 但先 `notifyListeners` 保证 UI 即时;损坏时 `load` 吞异常保持空态 ✓;启动竞态 🟡11。
- **Pro 门能否绕过**:UI 门完整;绕过面见 🟡10,不值得加固。
- **内购反馈**:`PurchaseService` 本身健壮(不可用/无商品/异常均写 notice),**但 notice 只在设置页被消费**(O6)。`onUnlocked → unlockPro()` 路径正确,恢复购买路径复用同一 stream ✓。
- **iOS 差异清单**:① heading 为 trueHeading(需定位授权),Android 为磁北(O1/O2);② iOS 精度:`LocationAccuracy.medium` = `kCLLocationAccuracyHundredMeters`,用户关「精确位置」后为 ~公里级,对历算无影响;③ iOS 无磁力计设备不存在(全系有),但 `headingAccuracy<=0` 时插件不发事件 → 保持「正北朝上」,行为反而比 Android 诚实;④ 显示名/权限文案未本地化(🟡8);⑤ `Info.plist` 允许横屏(🟡12);⑥ `NSLocationWhenInUseUsageDescription` 已在,无其他缺失键;`ITSAppUsesNonExemptEncryption=false` ✓。
- **Android 配置**:`INTERNET` 剥离 ✓、`uses-feature` gps/compass `required=false` ✓、`BILLING` 由插件并入 ✓、Gradle 内存已按 fieldstamp 先例调大 ✓。
- **性能**:O5。

### 3. 逻辑自洽(重中之重)
见上表与「逐项审」。一句话:**公式全对,窗口有错**。R1/R2 是唯一会让「算得对」变成「显示错」的地方,且两者同一修法。

### 4. 用户体验
- **主路径**:首启 → 今日页空状态(图标+引导+按钮)→ 切到机位页 → 「使用当前位置」→ 系统授权 → 自动切回?**不会自动切回**,用户留在机位页看到 snackbar「已使用你的当前位置」,还要自己点「今日」tab(4 步)。建议定位成功后 `onNeedLocation` 反向回调切回今日页,或空状态按钮直接定位(🟡7)。
- **读懂时间轴**:9 行「标题/副标题/时刻」结构清晰,已过时刻 0.45 透明度是好设计;日出/日落行带方位「太阳方位 58° NE」有单位有罗盘标;正午行带「太阳最高仰角 74°」。**缺**:各时段**持续时长**(黄金时段 60 min、蓝调 12 min 都没标),hero 只给起止;蓝调没有独立行,靠「晨光初现/蓝调时刻开始」+「黄金时段/早晨开始」两行夹出来,新手需要想一下。建议每段行尾加「· 60 分钟」。
- **切日期**:规划页左右箭头 + 点标题弹日历,Pro 门弹层清晰;免费用户在规划页看到的是与今日页**完全相同**的内容 + 一条 Pro 横幅,略显重复但作为 teaser 可接受。
- **信息密度 vs PhotoPills**:确实低——无地图、无 AR、无曝光/景深,一屏只讲光。楔子在产品上成立。
- **zh/en**:所有用户可见字符串均 `tr()`,含 `SavedLocation.fromJson` 的默认名;规划页日期格式按 locale 分支;罗盘 N/E/S/W 与方位缩写(`compassLabel`)在中文界面也用英文缩写——摄影圈通用,可接受。**未发现漏 `tr()`**。`ja` 只在壳设置页有,工具页回落英文,符合规则。
- **罗盘可读性**:图例只有「太阳/日落方向/月亮」,**日出射线(琥珀色)没有图例**,且与「当前太阳」同色;半径=高度这个编码没有任何提示(用户不知道点在中心=太阳在头顶)。
