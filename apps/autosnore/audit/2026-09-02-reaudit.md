## 插件行为核实(audioInterruption / iOS 后台 / onStateChanged)

**Android `AudioInterruptionMode.none`** = 根本不申请音频焦点,不是「申请但忽略」:`AudioRecorder.kt:53` `audioSession.apply(config, requestFocus=true)` → `AudioSessionManager.kt:52-54` `if (requestFocus && config.audioInterruption != NONE) requestAudioFocus(...)` 被跳过,焦点监听器(`:92-103`,把 `LOSS_TRANSIENT_CAN_DUCK` 也当 loss)根本不注册 → 通知音/闹钟不会触发 `recorderThread.pauseRecording()`(`AudioRecorder.kt:38`)。`RecordThread.kt:104-114` 循环持续 `pcmReader.read()`。顺带不再掐断用户白噪音。✅ 与首轮修法一致。
真正会停流的 Android 场景:① `PCMReader.kt:44-48` `read()<0`(如 `ERROR_DEAD_OBJECT`,audioserver 崩)→ throw → `RecordThread.kt:115-121` 线程退出 → `onStop()` → `RecordState.STOP` + 流 error;② Android 10+ 高优先级 app(通话/助手)抢麦时系统给**静音零样本**而非停流。两者都**没有恢复路径**:`_tryResume` 只在 `isPaused()==true` 时 `resume()`(`recording_controller.dart:172`),① 状态是 STOP、② 根本不失速。① 会被看门狗标 `stalled` 并在 `stop()` 时补记 `interruptedMs`(`:236`),报告能显示;② 完全不可见(dB 显示「—」,基线漂到底但 -50 地板兜住,事件为 0)。见 N-2。

**iOS `pauseResume` 对 `startStream` 生效**:中断处理在 `RecorderSessionExtension.swift:104-127`,是 `AudioRecordingDelegate` 协议扩展,file/stream 两个 delegate 共用;`RecorderStreamDelegate.swift:36` 在 `start` 时 `initAVAudioSession` 注册观察者。`.began` → `pause()`(`:112-114` → `RecorderStreamDelegate.swift:89-93` `engine.pause()` + `m_onPause`);`.ended` **仅当** `pauseResume` **且** `AVAudioSessionInterruptionOptions.shouldResume`(`:116-118`)→ `setActive(true)` + `resume()`(`:120-121` → `engine.start()` `:95-99`)。来电/闹钟正常带 `shouldResume`,会自动续流 ✅。缺口:① 无 `shouldResume` 或 `setActive` 失败(后台时别的 app 占着会话)→ 留在 pause;我们的 `_tryResume` → `resume()` 只调 `engine.start()`,**不重新 `setActive(true)`**,会话未激活时 `start()` 抛错、每秒重试一次一直失败;② `RecorderStreamDelegate.swift:116-128` 转换器出错(路由/输入格式变化,如夜里 AirPods 断连)→ `self.stop()` → `RecordState.stop`,插件没有 `AVAudioEngineConfigurationChange` 处理 → 同样无恢复。见 N-2。

**`IosRecordConfig(categoryOptions:[mixWithOthers])`**:`RecorderSessionExtension.swift:12-13` 固定 `setCategory(.playAndRecord, options:)` + `setActive(true, options:.notifyOthersOnDeactivation)`;`RecordConfig.swift:122` 把 `"mixWithOthers"` 映射为 `.mixWithOthers`——对 `.playAndRecord` 合法。配合 `UIBackgroundModes audio`,「会话激活 + 正在录音」满足 Apple 后台音频条件,锁屏后 tap 继续回调(`handleTap` 走 `DispatchQueue.main.async`,后台主线程照跑),Dart isolate 与 `_ticker`/`_checkpoint` 继续。注意我们把默认的 `defaultToSpeaker/allowBluetooth/allowBluetoothA2DP`(`ios_record_config.dart:21-25`)全部替换掉了 → 不走蓝牙麦,床头场景反而更稳。`applyHapticsPreference(false)`(`:16`)仍生效 = 记录期间系统提示音静音;`prefersNoInterruptionsFromSystemAlerts` 只在 `none` 时为 true(`:9`),iOS 用 `pauseResume` 所以为 false,闹钟仍会打断→结束后自动续。**以上需真机验证一次锁屏 30 min 后 dB 是否还在变**(Windows 无法验证)。

**`onStateChanged()` 在 stream 模式有事件**:`record.dart:59-68` `startStream` 先 `_initStateStream()`;`:124-125` `onStateChanged()` 返回同一个 broadcast controller(`record_state.dart:21`),多订阅安全;底层 `record_method_channel_mixin.dart:155-160` `receiveBroadcastStream`。Android `AudioRecorder.kt:101-116` 的 `onRecord/onPause/onStop` 与 file/stream 无关;`RecordThread.kt:106` 暂停时在循环里发 PAUSE。iOS `Recorder.swift:61-66` 给 stream delegate 挂同一组 `updateState` 回调(`:146-152`)。✅ `_onState` 会收到 `pause`;但 `stop` 被忽略(N-2)。

**看门狗与时钟(结论)**:
- `_audioMs += hole`(`:187`)**正确且必要,不会双重计时**:`elapsedMs`/`durationMs` 全用墙钟(`:150, :235`),`_audioMs` 只用来给事件盖时间戳(`:206`),`interruptedMs` 独立累加。不加 hole,洞之后所有事件会整体提前「洞长」。误差:hole 多算了一个正常 chunk 间隔(Android ≤160 ms / iOS ≈21 ms),洞前 `_buf` 残字节会与洞后数据拼成一个跨洞窗口(≤200 ms),可忽略。
- `_stallStartWallMs = _lastChunkWallMs`(`:154`)= 洞从最后一块音频算起而不是从发现时刻(晚 5 s)算起 → 洞长完整,语义正确;`stop()` `:236` 仍 stalled 时 `endMs - _stallStartWallMs` 口径一致。
- `_detector.reset()`(`detector.dart:112-117`)丢弃半截事件、保留基线 → 合理;iOS 中断后基线通常无需重学。
- `_tryResume` 在 `isPaused()==false` 时无操作:Android `none` 下唯一 pause 来源是我们自己(没有),所以 Android 上 `_tryResume` 事实上永远 no-op;真正停流(STOP/静音)无恢复,报告只靠 `interruptedMs` 兜底显示,「正在恢复…」文案在这类场景是**空承诺**。
