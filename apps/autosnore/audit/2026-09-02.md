> 范围:`D:\toolapp\apps\autosnore` 全部业务代码(`lib/**`、`test/**`、Android manifest、iOS Info.plist、pubspec)+ 实际锁定的插件原生源码(`record_android 2.1.2` / `record_ios 2.1.1` / `permission_handler_apple 9.4.10` / `wakelock_plus 1.5.2`,取自 `D:\dev\pub-cache`)。只读未改。已知且已修的 NSMicrophoneUsageDescription、PLAN 顶部的改名阻塞不再展开。

## 总评(3 句话)

检测算法与 UI 这层做得扎实(纯 Dart 可测、主题成体系、hero/表盘/空状态都到位),但**「整夜记录」这个核心承诺在真机上会被两处插件默认行为直接击穿**:iOS 上 `permission_handler` 因缺 Podfile 宏永远返回「拒绝」,一次记录都开始不了;两端一次普通通知提示音/闹钟就会让录音流永久暂停而 UI 继续走表,早晨得到一份「整夜安静、0 分」的假报告。修掉这两处 + 给停止/返回加一道防误触后,v1 才算真的能上真机验收。

## 🔴 阻断项

### R-1 iOS 麦克风权限永远「拒绝」,无法开始任何记录
- **文件**:`ios/`(**没有 `ios/Podfile`**);`lib/tool/recording_controller.dart:53-60`(`ensurePermission`);`lib/tool/recording_screen.dart:117-129`(`_Phase.denied` 面板)。
- **根因**:`permission_handler_apple 9.4.10` 的 `PermissionHandlerEnums.h:39-41` 把 `PERMISSION_MICROPHONE` 默认定义为 **0**;宏为 0 时 `AudioVideoPermissionStrategy.h` 走 `#else` 分支继承 `UnknownPermissionStrategy`,`status`/`request` 一律返回 `denied`(不弹系统授权框)。宏只能在 Podfile `post_install` 里通过 `GCC_PREPROCESSOR_DEFINITIONS` 打开;本 app 没有 Podfile,CI `build-ios.yml` 让 Flutter 用模板自动生成一份(`flutter_tools/templates/cocoapods/Podfile-ios`,零宏)。
- **用户看到**:点「开始记录」→ 转圈 → 「需要麦克风权限才能记录鼾声」+「重新授权」→ 点了还是同一页,系统从不弹授权框,系统设置里也找不到本 app 的麦克风开关(从未请求过)。
- **真机复现**:任意 iPhone 全新安装 → 首页点开始。
- **修法**(二选一,推荐 B):
  - A. 新建 `ios/Podfile`(拷 Flutter 模板)并在 `post_install` 的 `target.build_configurations.each` 里加 `config.build_settings['GCC_PREPROCESSOR_DEFINITIONS'] ||= ['$(inherited)', 'PERMISSION_MICROPHONE=1']`;**同工厂其它用 permission_handler 的 app 同样中招,要一起排查**。
  - B. 去掉 `permission_handler`,改用 `record` 自带的 `_recorder.hasPermission()`(两端都会真正弹框;iOS 拒绝即永久拒绝);Android 上要「永久拒绝」判定的话保留 permission_handler 仅在 Android 用。方案 B 少一个原生插件、少一个 Podfile 契约。

### R-2 一声通知/闹钟就让录音流永久暂停,UI 却继续走表——早晨拿到「整夜安静 0 分」的假报告
- **文件**:`lib/tool/recording_controller.dart:78-82`(`RecordConfig` 未设 `audioInterruption`,默认 `AudioInterruptionMode.pause`,见 `record_platform_interface-2.1.0/lib/src/types/record_config.dart:89`);`:83-85`(只 `debugPrint` 流错误);`:89-92`(`_ticker` 靠墙钟无条件涨);全文件**没有订阅 `_recorder.onStateChanged()`**。
- **插件实证**:
  - Android `record_android-2.1.2/.../recorder/AudioRecorder.kt:37-43`:`onFocusLoss → recorderThread?.pauseRecording()`,`onFocusGain` **仅当 `PAUSE_RESUME` 才 resume**;`AudioSessionManager.kt` 把 `AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK` 也当 loss。AOSP 的 `NotificationPlayer` 播每条通知音都申请 `TRANSIENT_MAY_DUCK` 焦点,闹钟申请 `TRANSIENT` —— 即**凌晨任何一条带声音的微信/短信/闹钟**都会触发。
  - iOS `record_ios-2.1.1/.../RecorderSessionExtension.swift` `onAudioSessionInterruption`:`.began → pause()`;`.ended` **仅 `pauseResume` 才 resume**。来电、Siri、闹钟、FaceTime 都是 interruption。
- **用户看到**:录音页时长照涨、「dB」停在最后一个值、鼾声计数不再变;早晨报告:时长 7h 正常、鼾声 0 次、评分 0「安静」、时间线空白——和真的安静一夜**完全无法区分**。
- **真机复现**:开始记录 → 用另一部手机给它发一条带提示音的消息(或设 1 分钟后的闹钟)→ 提示音后对着麦克风大声说话,观察 dB 是否还变。
- **修法**(三件一起做):
  1. `RecordConfig(..., audioInterruption: Platform.isAndroid ? AudioInterruptionMode.none : AudioInterruptionMode.pauseResume)`。Android 用 `none` = 根本不申请音频焦点,AudioRecord 在通知音期间照常采样(通话时系统会自行静音麦输入,不用管);顺带解决「点开始会掐断用户正在放的白噪音/播客」(`AudioSessionManager.apply` 申请 `AUDIOFOCUS_GAIN`)。iOS 必须 `pauseResume`,因为 interruption 后 `AVAudioEngine` 需要重新 `start()`。
  2. 订阅 `_recorder.onStateChanged()`:收到 `pause` 记 `gapStart`,收到 `record` 把 `_audioMs` 对齐到 `now - _startMs` 并把 `(gapStart, gapEnd)` 追加进 session 的 `interruptions` 列表。
  3. **失速看门狗**:`_ticker` 里若 `now - lastChunkWallMs > 5000 && running` → 先 `_recorder.resume()`,再失败 → `_finish(endedEarly: true)` 并给 session 标 `reason: 'stream_stalled'`。报告顶部横幅「录音中断 N 次,共 X 分钟」。

### R-3 一次误触(返回手势 / 单击停止)即结束整夜,无确认、不可撤销
- **文件**:`lib/tool/recording_screen.dart:101-105`(`PopScope` 在 recording 阶段拦住后**直接 `_finish(navigate: true)`**);`:297-311`(停止按钮单击即 `onStop`)。
- **用户看到**:床头手机被枕头/手臂蹭到屏幕边缘(Android 全面屏手势导航的边缘滑动 = 返回)→ 立刻结束并跳到报告页;早晨看到「00:47 结束」。R2 设计已把「离开前台」定为不可恢复,这条把误触也变成不可恢复。
- **真机复现**:记录中从屏幕左缘向右滑一下。
- **修法**:停止改为**长按 1.5 s**(`GestureDetector.onLongPress` + 进度环反馈)或弹确认框;返回手势在 recording 阶段 `canPop:false` 且只 `showSnackBar('长按停止按钮结束记录')`。

## 🟠 重要项

### O-1 整夜数据只在结束瞬间一次性落盘,进程死亡 = 整夜丢失
- `lib/tool/recording_screen.dart:54-63`(`_finish` 才 `addSession`)、`lib/tool/store.dart:83-87`。崩溃、电量耗尽关机、ROM 杀前台、Flutter 引擎 OOM,任一发生则 `_events` 随进程消失,首页什么都没有。
- 修:`RecordingController` 每 5 分钟把 `{startMs, events, audioMs}` 写到 `autosnore.inprogress.json`;`store.load()` 发现该文件即恢复为 `endedEarly:true` 的一晚并删除文件;正常 `stop()` 时也删除。

### O-2 报告页事件列表非懒加载,嘈杂/高灵敏度夜会卡死几秒
- `lib/tool/report_screen.dart:92-107`:`ListView(children: [... List.generate(events.length, ...)])` 一次性构建全部 `ListTile`。检测器上限约 1 事件/750 ms(minEvent 350 + mergeGap 400),8 h 理论上限 3.8 万条;现实中风扇+高灵敏度几百到几千条很常见。
- 修:`CustomScrollView` + `SliverList.builder`;或默认只列前 50 条 + 「展开全部」。

### O-3 报告页点「解锁 Pro」零反馈(商店不可用 / 商品未配 / 失败 / 成功都静默)
- `lib/tool/report_screen.dart:391-403` 直接 `PurchaseService.instance.buyPro()`;`notice` 只有设置页的 `_PurchaseNotices`(`lib/tool/autosnore_tool.dart:23, 178-207`)在监听。侧载/无 Play 账号时点了没任何反应;成功解锁的提示会**残留到下次打开设置页才弹**(过期误导)。另外 `_PurchaseNotices` 是壳 `core/purchase.dart:158-187` `PurchaseNotices` 的逐字复制。
- 修:在 `MaterialApp.builder` 里全局挂一个 `PurchaseNotices`(用壳的),删掉 tool 里的复制品。

### O-4 音频时钟(R1)没有任何与墙钟的校验;iOS 会持续漂移,打断时停走
- `lib/tool/recording_controller.dart:48, 118-119`:`tAudio = _startMs + 已处理窗口数×200ms`。
- Android:`PCMReader.kt` 直接 `AudioRecord(16000)`,无插件级重采样,帧数守恒,时钟基本准。
- iOS:`RecorderStreamDelegate.swift` tap `bufferSize 1024` 帧@硬件采样率(iPhone 通常 48 kHz);`AudioStreamProcessor.swift convertBuffer` 用 `AVAudioFrameCount(1024×16000/48000)` = **341(真值 341.33)截断做输出容量**,每回调少交付 ⅓ 帧 → 每秒约 −1 ms → 8 h 约 **−29 s**;44.1 kHz 机型 371.5→371 同理。事件时间戳/时间线整体前移半分钟,未致命但需真机确认。
- 任一暂停(R-2)期间时钟停走,恢复后所有事件的时刻都比真实早出「暂停时长」。
- 修:`_ticker` 每秒比较 `wall = now − _startMs` 与 `_audioMs`,`wall − _audioMs > 2000` 时 `_audioMs = wall` 并记 gap;把 `audioCoverageMs`(= 累计 `_audioMs`)存进 `SleepSession`,报告里显示「有效覆盖 X%」。

### O-5 灵敏度滑杆在安静卧室里基本失效
- `lib/tool/detector.dart:45, 70-71`:`threshold = max(baseline + {6|12|18}, absoluteFloor −50)`。手机麦在安静卧室的 RMS 底噪常在 −60 ~ −70 dBFS;基线 ≤ −62 时「高」和「中」都被 −50 地板顶住(同为 −50),「低」也只有 −47。用户拨到「高」抓不到更多轻鼾,拨到「低」也几乎不减少。
- 修:地板随灵敏度平移 `absoluteFloorDb = −50 − (sensitivity − 0.5) × 16`(高 −58 / 中 −50 / 低 −42);或直接把地板降到 −60 并把 `minEventMs` 提到 450 防底噪抖动。补一条单测「基线 −65 时三档阈值必须互不相同」。

### O-6 开始前没有把「要插电、屏幕常亮、锁屏或切走即结束」说清
- 现状:商店文案有「keep it charging / keeps the screen on」(`store/listing.md:42-44, 98-99`);首页空状态一句「接通电源」(`home_screen.dart:51-53`)——**只在没有历史时显示**;录音页底部一行 `bodySmall` 灰字(`recording_screen.dart:287-295`);**「锁屏 / 切到别的 app 记录就结束」只在事后横幅里说**(`report_screen.dart:130-135`)。首页 hero 一点就直接进权限→录音(`home_screen.dart:84-86`)。
- 修:首次(或每次,带「不再提示」)点开始前弹一张 3 行清单:① 接通电源 ② 屏幕会整夜常亮,建议屏幕朝下/调低亮度 ③ 锁屏、来电接听、切走 = 记录结束。iOS 顺带说明「记录期间系统提示音与震动会被静音」(见 O-7 c)。

### O-7 iOS / Android 差异清单(需写进 PLAN §9,部分要改代码)
- a. **`UIBackgroundModes audio` 前台方案不需要**;但反过来:iOS 只要加这一项 + 现有的 `.playAndRecord` 活动会话,**锁屏后 AVAudioEngine 会继续采样、Dart isolate 不挂起**(SnoreLab 等正是这么做)。iOS 的「v1.1 后台采麦」成本远低于 Android 的前台服务,建议 v1.1 先做 iOS。
- b. **点开始会掐断用户正在播放的白噪音/助眠音**:iOS `applyCategory` 用 `.playAndRecord` 且 `iosConfig.categoryOptions` 默认为空(无 `mixWithOthers`),`setActive(true)` 会中断其它 app 音频;Android 申请 `AUDIOFOCUS_GAIN`(R-2 的 `none` 方案顺带解决)。修:`iosConfig: IosRecordConfig(categoryOptions: [IosAudioCategoryOption.mixWithOthers])`。
- c. iOS `applyHapticsPreference(false)`(插件默认)= 记录期间**系统提示音与震动全部静音**——对睡眠是好事,但用户收不到闹钟以外的任何响声,文案要说。
- d. **PCM 回调频率两端差 5~8 倍**:iOS 每 ~21 ms 一次(1024 帧@48 k → 341 帧@16 k = 682 B),≈47 次/s 走主线程 `DispatchQueue.main.async → EventSink`;Android `minBufferSize×2` 通常 2.5~5 KB,≈6~12 次/s。`_onChunk` 的 `BytesBuilder` 聚合到 6400 B 再算,算法不受影响;iOS 整夜约 135 万次平台消息,可接受但值得在真机看 CPU/电量。
- e. iOS 拒绝一次即 `permanentlyDenied`(`AudioVideoPermissionStrategy.m:59-62`),`_Phase.denied`「重新授权」分支在 iOS 永远走不到——文案没问题,只是逻辑要知道。
- f. 锁屏行为一致:两端按电源键都触发 `paused` → R2 结束。iOS 的通知中心/控制中心下拉只触发 `inactive`,记录继续,正确。
- g. **从系统设置授权回来,页面仍停在「永久拒绝」**:`recording_screen.dart:85-89` 的 `resumed` 分支只处理 `_saved && _pending`;用户开完权限回到 app 还得点「取消」再进一次。修:`resumed && _phase == permanentlyDenied → _begin()`。

### O-8 「安静一夜」「短测试」「被打断的夜」三者在报告/趋势里不可区分,评分都是 0
- `lib/tool/models.dart:125-129`:`durationMs > 500` 就算一晚,0 事件 = 0 分「安静」进历史与趋势平均(`trends_screen.dart:33-34`)。验收清单第 2 条「录 1 分钟发几声呼噜」会得到「评分 40 中等」这种荒谬值(1 分钟 5 声 = 300 次/小时封顶 60 → +30)。
- 修:session 存 `audioCoverageMs` + `interruptions`(O-4/R-2);报告顶部横幅规则:时长 < 60 min → 「短记录,评分仅供参考」;覆盖率 < 90% → 「记录不完整」;趋势页平均只算 ≥ 3 h 且覆盖率 ≥ 90% 的夜,其余灰显。

## 检测算法审阅结论(逐项 ①-⑦)

- **① 响度**(`audio_math.dart`):`getInt16(LE)/32768` 处理有符号 PCM 正确,dBFS-RMS 定义正确(满幅方波 0 dB、正弦 −3 dB),窗长 200 ms(3200 采样)合理。缺直流去除(Y-4)。`_onChunk` 的 `sublistView` + `ByteData.sublistView` 偏移处理正确。
- **② 自适应基线**(`detector.dart:54, 98, 89-93`):初值 −55;EMA α=0.05/200 ms,时间常数 4 s,仅在阈值以下更新(含事件内的短暂低谷)——稳妥。R3 的 20 s 封顶 + `_baseline = db` 能正确压住风扇/空调;副作用是 (a) 封顶事件本身进统计(Y-2),(b) snap 到瞬态噪声(卡车 20 s)后约 9~10 s 失聪——可接受。连续无 400 ms 低谷的极响鼾声者会被反复切成 20 s 段并 snap,但真实鼾声呼气段几乎必有低谷,风险低。
- **③ 事件判定**:阈值 = 基线 + 12 dB(6~18),无幅度滞回但 `mergeGap 400 ms` 起到时间滞回,`minEventMs 350`(实际需 3 个窗口 ≈ 600 ms 音频)可滤点击。取值合理;时长少算一窗(Y-3);地板 −50 主导阈值让滑杆失效(O-5)。
- **④ 节律性**(`models.dart:103-121`):相邻事件起点间隔 1.5~8 s 即算节律,双向看邻居,统计正确。风扇(无事件)不会误判;伴侣说话的句间停顿 1~3 s 会被算成节律、滴水/挂钟会被算成节律——文案已定位为「更可能」,且不进评分,可接受。建议把窗口收到 2~6 s 并要求「连续 ≥3 个事件成串」才算节律,更贴呼吸周期。
- **⑤ 评分**(`models.dart:125-137`):`min(100, 占比×2 + min(指数,60)×0.5)`,单调、有界、`durationMs ≤ 0` 返回 0——数值上自洽。语义问题在 O-8:0 分既是「安静」也是「没数据」,短夜评分虚高。
- **⑥ 灵敏度**:只映射到 `effectiveThresholdDb`(`detector.dart:45`),不动地板、不动 `minEventMs`;在安静房间几乎无效(O-5)。
- **⑦ 报告统计**:次数/指数/占比/最响均为 `events` 的纯 getter,与原始事件一致 ✓;时间线 48 桶按起点分桶、取桶内峰值,映射 −60~−10 dB ✓(事件峰值不可能低于 −50,所以最低柱高 ≈ 0.3);`durationMs` 用墙钟 `endMs`、事件用音频钟,漂移时桶位轻微偏移(O-4)。CSV 与报告口径一致但时间精度丢失(Y-5)。

## 五维度逐项结论

### 1. 产品设计
- 核心承诺 vs v1 限制:**没说清**「锁屏 / 切走就结束」,只在事后横幅承认(O-6);「插电、常亮」说了但位置弱。
- 医疗承诺:合规,无「诊断」类词;关键词有轻微越界(Y-13)。
- 免费 3 晚:门卡在历史留存,免费层完整可用 ✓;裁剪无预警(Y-12)。趋势/对比需 Pro 且 ≥2 晚——免费用户手里正好有 3 晚却看不到任何对比,可考虑免费给一个 3 晚迷你趋势当 Pro 引流。
- 评分:公式合理但意义未解释(Y-8),「安静 = 无数据」会误导(O-8)。
- 改名阻塞未执行(已知,不重复)。

### 2. 代码实现(真机会坏什么)
- 权限流:Android 三态 + 去设置 ✓;**iOS 永远拒绝(R-1)**;从设置回来不刷新(O-7 g)。
