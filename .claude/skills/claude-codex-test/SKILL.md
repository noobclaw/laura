# Claude × Codex 遊戲接手測試（claude-codex-test）

用戶的遊戲流水線（2026-11-28 定）：

- **Codex 負責第 1–12 步**：用 `codex-game-super-skill` 選熱門賽道 → 拆原版 → 還原策劃、數值、關卡 → 對齊原版 → 重寫底層（不得和原版代碼重複）→ 創新玩法、故事背景、新策劃與數值 → 寫代碼 → 定美術方向與引擎 → 用 gameartstyle.loopyhop.com 的提示詞配 img2.5 生圖 → 替換全部原版美術與動效 → 自測 → 推 GitHub。
- **Claude 負責第 13–19 步**（本 skill）：接手 → 獨立寫測試用例 → 審計並修代碼 → 驗美術與動效、寫修復要求 → 複驗 → 內購、定價、Steam → 上架。

本 skill 也是流程裡說的「claude-game-review」。帳號版叫 `codex-handoff-test`（帳號 skill 名稱不能含 claude），內容相同。

**驗收標準不在這裡重新發明**：美術、動效、好玩、爽感的標準全部照 `casual-game-production`（休閒）或 `large-game-production`（大型）原文執行，第五節列出原文條目。Claude 的職責是逐條驗、打分、開單，**不能比原文寬鬆**。兩者衝突時，標準以那兩個 skill 為準，分工與交接以本 skill 為準。

## 一、四條硬規矩

1. **美術圖片和動效 Claude 不動手。**（用戶 2026-11-28 原話：涉及美術圖片、動效你不管，給出修復要求和文檔提交到 GitHub，我讓 Codex 來修復。）Claude 不改、不生成、不替換：圖片、圖集、圖示、背景、生圖提示詞、粒子、動畫、緩動曲線、特效時長和強度、著色器、材質、光照、後處理、配色、視覺風格、音效素材。發現問題只寫 `ART-FIX` 文檔（第六節），提交到 GitHub，由 Codex 修。
   - 判斷法：**改完之後畫面或動態看起來會不一樣嗎？會 → 交 Codex。**
   - Claude 可以改的「看得見的代碼」只限功能性錯誤：文字截斷或溢出、按鈕點不到、安全區遮擋、層級蓋住可操作元件、多語言字串缺漏。修的方式不得換圖、改動效、改配色。拿不準就寫進 ART-FIX。
2. **測試用例獨立寫。** 先只讀策劃書和數值表寫 Claude 自己的用例，寫完才看 Codex 的測試和驗收記錄，再比對差異。
3. **證據說話，狀態如實。** 每個「通過」都附測試名、數字、截圖檔名或代碼位置。沒跑過的寫「未評估」，未評估不算通過。好不好玩、手感、聲音，在真人玩過、人耳聽過之前一律寫「未經人玩過／未經人耳」。
4. **不碰原版的代碼與素材。** Claude 不反編譯、不下載原版安裝包。Codex 交來的原版拆解材料只用來查重和對照規則，不複製任何一行代碼、文案或素材。

## 二、分支與產物位置

- Codex 的分支：`codex/<game>-web`（或交接說明裡寫的分支），遊戲在 `apps/<game>/`。
- Claude 的工作分支：從 Codex 分支切出 `claude/<game>-qa`。Claude 不直接推 Codex 的分支。
- Claude 的產物全部放 `apps/<game>/qa/`，證據放 `apps/<game>/qa/evidence/`：

| 檔案 | 內容 | 步驟 |
|---|---|---|
| `INTAKE.md` | 交接包清點、基線測試結果、缺件 | 13 |
| `TEST-CASES-claude.md` | Claude 獨立用例 | 13 |
| `AUDIT.md` | 代碼、玩法、關卡、數值、淨室審計 | 14 |
| `ART-REVIEW-<YYYYMMDD>.md` | 美術與動效逐條打分（第五節） | 15 |
| `ART-FIX-<YYYYMMDD>-<n>.md` | 美術動效修復要求（交 Codex） | 15 |
| `TC-RESULT-<YYYYMMDD>.md` | 每輪用例執行結果 | 14、17 |
| `MONETIZATION.md` | 內購、廣告、定價、Steam | 18 |
| `RELEASE-CHECKLIST.md` | 各平台上架清單與狀態 | 19 |
| `QA-REPORT.md` | 總驗收報告（完工清單八道） | 每輪結束 |

- 提交訊息用英文，小步提交、立刻推送（至少每 30 分鐘一次）。
- 拉倉庫：公開倉庫用唯讀拉取即可；要推送時才申請推送權限。被拒時把修改做成 patch 交給用戶，並說明需要哪個倉庫的推送權限，不繞路。

## 三、第 13 步：接手與獨立測試用例

### 3.1 拉取與清點

1. 淺拉 Codex 分支（大倉庫加 `GIT_LFS_SKIP_SMUDGE=1`，逾時給足 10 分鐘）。
2. 讀遊戲目錄的 README、PLAN、ACCEPTANCE、START、驗收記錄，以及倉庫根目錄 `CLAUDE.md`。
3. 按下表清點，寫進 `INTAKE.md`。缺「必須」項時標「缺件」並寫一份交 Codex 的補件要求；補齊前，依賴它的用例全部標「未評估：缺策劃」。

| 交接項 | 必須 | 用途 |
|---|---|---|
| 新版策劃書（世界觀與故事、核心循環、系統清單、每個系統的規則） | ✅ | 獨立用例的唯一來源 |
| 數值表（經濟、體力、獎勵、價格、難度曲線） | ✅ | 數值審計、30 天模擬 |
| 關卡表（每關教什麼、考什麼、組合什麼、目標時長與勝率） | ✅ | 關卡審計 |
| 原版對照表（原版規則 → 已做／改了／故意不同） | ✅ | 對齊與創新核對 |
| 創新清單（新增或大改的玩法，各自解決什麼問題） | ✅ | 檢查是否比原版好 |
| 美術規格九節（視覺定位、氛圍、形狀語言、色板、角色、場景、介面、素材標準、參考方向）＋ 2D/2.5D/3D、引擎、物理、光照、材質的決定 | ✅ | 美術驗收基準 |
| 素材登記表（每個檔：來源、生成工具、提示詞、授權、改動） | ✅ | 淨室與授權 |
| Codex 的交付前自評四項（爽感對照表、好玩標準打分、並排截圖、≥10 秒動態） | ✅ | 第五節比對；缺了記 P1 |
| 可運行版本與啟動方式 | ✅ | 試玩、截圖 |
| Codex 自己的測試與驗收記錄 | ✅ | 3.3 比對用；寫完自己的用例前不看 |
| 原版拆解材料（反編譯源碼清單、原版素材哈希、原版截圖） | 建議 | 查重、並排；沒有就標「無法做原版比對」 |

4. **基線**：照 README 跑全部測試和構建，記錄命令、版本、通過數、耗時。基線就紅的先記下來，不在紅的基線上做審計結論。

### 3.2 寫 Claude 自己的測試用例

只讀策劃書、數值表、關卡表、創新清單、美術規格來寫。每條需求至少一條用例。欄位：

```
| TC-區塊-序號 | 對應策劃條目 | 前置條件 | 步驟 | 預期（可判定） | 類型 | 自動/手動 | 優先級 |
```

類型至少覆蓋以下十三類，每類都要有用例：

1. **規則**：正常、邊界、非法輸入；動畫播放中輸入；連點。
2. **關卡**：每關可解（無道具）、目標時長、星級門檻、教學順序。
3. **數值與經濟**：每種資源的來源與去處；30 天不付費模擬的四條及格線。
4. **進度與存檔**：壞檔、缺欄位、NaN、負數、舊版本遷移、多分頁衝突、寫盤失敗。
5. **生命週期**：切背景、回前景、斷網、旋轉螢幕、系統減少動效。
6. **刷資源**：改系統時間、重開刷獎勵、退出規避失敗、重複領獎憑據。
7. **變現**：每個付費入口先出付費頁、恢復購買、本地價格、隨機獎勵公開機率、插頁不在前幾關也不打斷進行中的一局、商店未接通時不模擬購買成功。
8. **多語言**：每種語言每個畫面的溢出與斷行；由右至左語言；數字與日期格式。
9. **性能**：最熱鬧時刻幀率、連玩 30 分鐘記憶體與粒子數、連打 10 局不殘留。
10. **美術與動效**：第五節每一條都落成至少一條用例（只驗不改）。
11. **語言切換**：4.5 節「語言切換方不方便」每一條。
12. **分享**：4.5 節「分享」每一條。
13. **引導評論**：4.5 節「引導評論」每一條。

用例統計數用腳本算，不手數。

### 3.3 比對 Codex 的測試

寫完自己的用例後再讀 Codex 的測試和驗收記錄，列表比對：Codex 有、Claude 沒有的判斷是否補；Claude 有、Codex 沒有的是 Codex 自測盲點，記入 `AUDIT.md`。Codex 驗收記錄裡的每個說法都要找到對應測試或證據，找不到的標「僅記錄所述，未證實」。

## 四、第 14 步：審計與修復

### 4.1 代碼審計（完工清單第 4 道）

逐項寫「發現／嚴重度／已修或為何不修」：主迴圈錯誤保護（單幀出錯不凍住，錯誤記錄並在角落顯示）；規則與畫面分離（規則層能脫離引擎跑測試，畫面只播事件）；存檔版本號、遷移、原子寫、壞檔修復；計時器、監聽、動畫與擁有者同生同死；非同步競態（連點、動畫中或暫停中輸入、請求被取代、節點已銷毀）；物件池和陣列有上限；依賴版本鎖定、授權齊全、不從網路即時載入；主控台錯誤與警告逐條追來源。

嚴重度：**P0** 崩潰、卡死、丟存檔、付費錯誤、會被拒審；**P1** 玩家看得到的錯誤、數值失衡、關卡不可解；**P2** 打磨。

### 4.2 玩法、關卡、數值審計（完工清單第 3、7 道）

- **機器人跑完整內容**：用規則層 API 寫無頭機器人，至少兩種策略（隨機亂玩、照提示或貪心）。每關輸出勝率、步數、時長、星級、道具用量，和關卡表目標比；兩種策略的勝率差證明選擇有意義。
- **可解性**：至少全部教學關和每章首尾證明無道具可解；其餘關卡分清「無道具可解」和「用了輔助才過」，不混稱。
- **30 天經濟模擬**：「不看廣告」和「看獎勵廣告」兩種玩家，按天輸出進度、資源存量、當天升級次數、廣告次數。及格線：不卡死；不出現連續 3 天當天升級次數為 0 或資源頂到上限不動；付費品到第 30 天仍有用；寫出第一章在第幾天打完並和品類頭部比。
- **每關教什麼、考什麼、組合什麼**：逐關確認確實做到。
- **原版對照**：原版對照表每一行核實；「故意不同」要有理由。
- **創新是否更好**：每條創新寫出解決原版哪個問題，用機器人數字或試玩證據說明是否達到；達不到標「未達到」，不寫「應該更好」。
- **好玩標準八條**（casual 原文）逐條打「通過／部分／不通過／未評估」：獎勵密集（每 15–30 秒一次看得見的成長或選擇，錄屏數間隔）、每局有高潮（至少 1–2 次「大」級反饋）、輸了不白玩、一個招牌動作或聲音、角色有梗（台詞原創）、可分享、每天回來的理由、廣告拍什麼遊戲就有什麼；紅線（不做付費抽角色、焦慮倒數、針對未成年、隨機獎勵公開機率）。
- **八條驗收標準**（casual 原文）逐條打分附依據。

### 4.3 淨室查重

- **代碼**：有原版拆解源碼時，跑重複片段檢測（去掉空白和識別符後按 token 序列比對），列出相似片段和位置；超出常用語法的相似一律記 P0，交 Codex 重寫。沒有原版源碼時寫「無法做原版代碼比對」。
- **素材**：運行時引用的每個圖片、音效、字型都在素材登記表裡；和原版素材做位元組哈希比對，有條件再做感知哈希；引用到舊素材路徑的數量必須是 0。素材問題屬於美術，寫進 ART-FIX。
- **文案與名稱**：原版的角色名、關卡名、介面文案、商店文案不出現在我們的遊戲和商店頁。

### 4.4 修 bug 的規矩

- 只修第一節允許的範圍：規則、邏輯、數值資料、存檔、生命週期、變現邏輯、多語言字串、功能性排版錯誤。
- 每個修復一個提交，附一個修前失敗、修後通過的回歸測試。
- 改數值前在 `AUDIT.md` 寫原值、新值、理由和模擬結果；影響策劃書的同步改策劃書。
- 每輪收尾跑全部測試和構建，結果寫進 `TC-RESULT`。偶發失敗記下來查原因，不能重跑到綠就算數。

### 4.5 三項必查：設定切換語言、分享、引導評論（用戶 2026-11-28 要求，每輪都驗）

標準取自 `tool-app-factory` 十三條鐵律第 7、10、13 條和 casual 好玩標準第 6 條。每項打「通過／部分／不通過」，附截圖和點擊次數。語言切換不過算完工清單第 1 道不過；分享或引導評論不過算第 2 道不過。

**語言切換方不方便**

- 入口：首頁一個齒輪點進設定，語言放在設定第一行。從首頁到改好語言不超過 3 次點擊，實際點擊數寫進報告。
- 選項用該語言自己的名字顯示（English、日本語、العربية），不用國旗代替。
- 切換即時生效：不重啟、不丟當前一局、設定彈窗不關；彈窗、結算、商店、提示文字全部跟著換。
- 記住選擇，重開仍是該語言；首次啟動跟隨系統語言，系統語言不支援時用英文。
- 局內（暫停選單）也能進設定切換。
- 列出的每種語言都完整，沒有半翻譯；沒做完的語言不能列出來。

**分享**

- 結算畫面和成就時刻（勝利、破紀錄、集齊相冊一頁）有明顯的分享按鈕，一鍵叫起系統分享（iOS 分享面板、Android Sharesheet、網頁 Web Share API；不支援時下載圖片）。
- 分享出去的是 1080×1350 成果卡：遊戲名、關卡、星級、用時，加一個好笑的統計，附商店連結；不含個人資料。
- 首頁或設定也有「分享遊戲」入口。
- 怎麼驗：瀏覽器裡攔截 `navigator.share` 看傳了什麼；把成果卡存到 `qa/evidence/` 打開看。

**引導評論**

- 時機：成就時刻（首次三星、過第 N 關、集齊一頁相冊）；不在失敗後、不在第一次開啟、不打斷進行中的一局；同一玩家間隔至少 30 天。
- 兩步法：先問「喜歡這個遊戲嗎？」，喜歡才叫系統評分（iOS `requestReview`、Android Play In-App Review）；不喜歡就引到意見回饋。
- 設定裡常駐「給我們評分」，點了打開商店評分頁。
- 紅線：不用獎勵換評分、不自己畫星星、不預設五星（Apple 5.6.1、3.2.2）。
- 網頁版沒有系統評分時，觸發邏輯和時機要先做好，接平台時直接接上；網頁版標「待平台接入」，不算通過。

## 五、第 15 步：美術與動效驗收標準（照遊戲製作 skill 原文，不得放寬）

每條打「通過／部分／不通過／未評估」，附證據檔名，寫進 `ART-REVIEW-<日期>.md`。「部分」和「不通過」都開 ART-FIX。截不了圖或錄不了動態的項目標「未評估：無法截圖」，不憑讀代碼下結論。

### 5.1 精美度標準七條（用戶 2026-11-22 定，2026-11-25 改）

參考作：《星隕戰紀 Starfall》（sanwan.ai/games/xingyun-moba，公開復刻版 vileosbot-bot/starfall-rebuild）。它的美術和音效全是程式生成，「沒有美術素材」不是做不到的理由。缺一不可：

| # | 標準 | 怎麼驗 |
|---|---|---|
| S1 | **3D 或高品質 2D 擇一做到位。** 3D：透視鏡頭、方向光、環境光、陰影，角色統一 Q 版比例。2D：每個角色和物件是完整插畫或向量圖，統一粗描邊、兩階明暗、高光，會動的部位拆成骨骼部件。不用平面色塊、不用幾何體拼角色。選原作或頭部競品用的那一種。 | 截圖逐張看；對照美術規格的維度決定 |
| S2 | **完整環境。** 主體不浮在空白或純色上；有地面、植被、水、石頭這類場景物件；畫面四角都有內容。 | 每個場景截圖看四角 |
| S3 | **模型有細節。** 角色和主要物件由多部件組成，有材質區分、高光、明暗，一眼認得出是什麼。 | 縮到遊戲實際尺寸看 |
| S4 | **介面成品水準。** 按鈕、面板、圖示、數字有立體感和統一風格，不用瀏覽器預設樣式。 | 每個介面畫面截圖 |
| S5 | **畫面是活的。** 靜止不操作時也有東西在動：光在閃、水在流、角色在呼吸。 | 不操作錄 10 秒 |
| S6 | **操作有即時反饋。** 見 5.3–5.5。 | 手感矩陣 |
| S7 | **手機和電腦都對。** 至少一個直屏手機尺寸（390×844）和一個橫屏尺寸。 | 兩個尺寸各截全套 |

**否決規則**：把我們的截圖和 Starfall、原版或頭部競品同類畫面並排，明顯差一截就是不通過。自評不能比並排圖寬鬆：看並排圖覺得差，就是差。

### 5.2 美術規格與素材檢查

- **美術規格九節齊全**，每節逐條對照實際畫面打分；參考方向寫明從每個參考取什麼、避開什麼。
- **主視覺樣板**放在真實遊戲畫面裡、用手機實際尺寸看過。
- **成套一致**：共用同一色板、視角、光源方向、描邊、細節密度。做一張所有物件的拼圖（contact sheet），任何一張跳出來就不通過。
- **AI 生成圖逐張檢查**：尺寸、是否真透明、有沒有被裁切、有沒有多餘的字或簽名、縮到遊戲尺寸還看不看得清。
- **介面文字用程式排**，不畫進圖裡；按鈕圖不帶字。
- **決定遊戲長相的主角、棋盤、背景、介面是原創**；免費素材庫只用於粒子貼圖、音效、小圖示這類通用件，只取 CC0 / CC-BY。
- **素材登記表**每個檔一行：檔名、來源、原檔名或生成工具與提示詞、作者、授權、改動；CC-BY 素材在製作名單署名。
- **原版素材殘留為 0**（4.3）。
- **文化與地區敏感度**：目標市場不接受的字眼、符號、圖案逐張檢查。

### 5.3 爽感：打擊感十項（每個命中、擊殺、受傷、消除、放對事件逐項核對）

1. 打擊停頓：輕擊約 2 幀、重擊 8–10 幀，首領擊殺更長，攻擊者和目標一起停，用真實時間計時。
2. 受擊白閃約 0.1 秒；有屬性的閃對應顏色。
3. 擊退：會衰減的速度推開 0.2–0.4 秒，不瞬移；傷害越大推越遠。
4. 命中點特效：接觸點星花或波紋，方向跟攻擊方向，不只有數字。
5. 發射有樣子：投射物有拖尾，出手有閃光或動作。
6. 震屏分級：不同事件不同強度，只動鏡頭。
7. 死亡儀式：碎片、煙霧，掉落物飛向介面計數器。
8. 留下痕跡：焦痕、碎片、水漬停留一陣子。
9. 聲音疊層：高頻清脆 + 低頻重擊，大事件加低音。
10. 慢動作只給大場面。

休閒類沒有戰鬥時，把「命中」對應到「放對一步、消除一組、連擊、過關」，十項中不適用的標「不適用」並寫原因。

### 5.4 爽感：節奏六項（large 原文，各打 0–2 分）

1. 力量幻想：越玩越強，後期能一次清一大片；難度靠數量不靠刻薄。
2. 獎勵密度：每 10–20 秒一個小獎勵（casual 為 15–30 秒）；自動跑一局記錄每次獎勵時間，最長間隔不超過標準。
3. 稱讚逐級升級：連擊越多，字越大、音越高、粒子越多。
4. 組合的「啊哈」：至少幾組組合後變質，配「大」級反饋。
5. 操作密度：動作類每分鐘至少 15 次有意義操作；全自動只能看的時間不超過一局一半；放置類每次回來至少 3 件事可做。
6. 輸了也有收穫，一局裡有幾個「我很強」的瞬間。

**總分低於 9 不通過。**

### 5.5 三級反饋表與手感規則（casual 原文）

| 級別 | 用在哪 | 粒子數 | 配套 |
|---|---|---|---|
| 小 | 標記、按鈕、切換 | 0–4 | 短促音效 |
| 中 | 放對一步、消除一組 | 6–12 | 彈跳、光環、音效、輕震 |
| 大 | 過關、連擊高潮、破紀錄 | 20–40 | 全屏效果、稱讚字、煙火、星星、音樂短句、震動 |

逐條檢查：

- 同一級的事件用同一套強度，整個遊戲成比例。
- 會動的東西都用緩動：彈出用回彈、落定用減速、蓄力用加速。
- 稱讚只根據「沒有違反規則」，不根據「符合答案」。
- 做錯立刻知道錯在哪，但不羞辱：抖動、變色、提示原因。
- 每個效果結束回到原位，不殘留縮放、位移；效果結束粒子數歸零。
- 日常操作不過度反饋。
- 大面積閃光每秒不超過 3 次。
- 設定裡有音效開關、震動開關、減少閃光、減少動態，系統開了「減少動態效果」時自動降級，且真的生效。
- 動畫時長不決定規則結算；動畫播放中的輸入被忽略或排隊。
- 特效放大遊戲本來的感覺，不蓋住讀局資訊。

### 5.6 必交證據與總判定（交付前自評四項 + 完工清單第 6 道）

Claude 獨立重做一遍，不採信 Codex 的自評結論：

1. **手感矩陣**：每種事件 × 打擊感十項，每格「已有／缺／不適用」。有「缺」又沒寫原因 → 不通過。
2. **好玩度打分**：好玩標準八條 + 節奏六項（總分 ≥9），附數字（獎勵間隔、每分鐘操作數、一局時長）。
3. **並排截圖**：自己和 Starfall、原版或頭部競品同類畫面並排一張，存 `qa/evidence/`。
4. **動態**：固定種子錄 ≥10 秒或拼 12 張連續幀，自己看過；看有沒有閃白、擊退、特效、留痕、空場。
5. **戰鬥幀率**：最熱鬧時刻量（不是空場景），手機尺寸和桌面尺寸各一次；連玩 30 分鐘粒子數、節點數、記憶體不持續上漲。

**美術與動效判定**：5.1–5.6 全部「通過」或「不適用（有原因）」才算美術動效驗收通過；任何「部分」「不通過」都開 ART-FIX；任何「未評估」都不算通過。音效和音樂沒有人耳聽過，不能說好聽。

## 八之一、命名、包名與 GEO（用戶 2026-11-28 定）

**包名**：遊戲一律用 `com.laura.<遊戲名>`（例：`com.laura.cozydays`）；工具類 App 繼續用 `com.noobclaw.<名>`。包名在 App Store Connect 建 App 記錄後就不能改，建之前先確認。

**GEO（生成式引擎優化）**：讓 ChatGPT、Gemini、Perplexity、Google AI 摘要這類 AI 引擎能認出這款遊戲，並在玩家問「有什麼好玩的 X 類遊戲」時推薦它。依據：AppTweak 分析 12.5 萬則 ChatGPT 推薦，AI 把 App 當「實體」理解，看任務契合、定位清楚、新鮮度和外部驗證；各處描述不一致時會被當成模糊實體；遊戲推薦的引用來源中 App Store 頁約佔 42.6%、Google Play 約 16%，Reddit 和 Wikipedia 的引用是一般 App 的 5 倍；玩家找遊戲是按類型、IP、氛圍和「像哪款遊戲」來找。

上架前逐條檢查，寫進 `RELEASE-CHECKLIST.md`：

1. **名稱是清楚的實體**：先查 App Store 同名和近似名、AI 引擎問「<名稱> game」會不會指到別人；商店名 = 品牌詞 + 玩法詞（例：「Cozy Days: Sort & Tidy Up」），讓 AI 一眼歸類。被佔用時不硬擠，改品牌詞或加玩法詞。
2. **一句話定位，處處一致**：類型、主題、特色、什麼時候玩，寫成一句，原樣用在商店名、副標題、描述第一句、官網、新聞稿、社群帖。不同平台（App Store、Google Play、Steam）用同一個名稱字串。
3. **商店頁寫成可被引用的事實**：描述開頭直接說「X 是一款……的遊戲，玩家……」；列出可驗證的特色（關卡數、離線、語言）；更新說明寫具體改了什麼。
4. **自有網頁**：一個正式頁面，名稱和定位與商店一致，放 schema.org 的 `VideoGame` 結構化資料、常見問題、`llms.txt`。
5. **社群與第三方**：在相關 subreddit、論坛、影片平台有真實的討論和試玩；不買評論、不寫假評論。
6. **多語言**：各地區的本地化名稱保留同一個品牌詞。
7. **商標**：品牌詞在美國（USPTO 第 9、41 類）和目標市場查過，結果寫進文件；Claude 的網頁查詢只算初查，不是法律意見。
8. **每月量測**：用固定問題（「best cozy sorting game」「games like <頭部競品>」）在 ChatGPT、Gemini、Perplexity 各問一次，記錄有沒有出現、怎麼被描述，據此修定位。
